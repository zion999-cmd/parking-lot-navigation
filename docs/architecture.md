# 系统架构边界

本文件**只记录已经确定的边界**。

- **P0001**（摄像头节点）已实现。
- **P0001.1**（配网 + OTA）已实现 —— 它们是**摄像头节点内部的基础设施**，
  不改变第 3 节的任何边界，也没有引入新的业务概念。
- 其它模块都还没开始实现，因此这里只写它们的职责边界和接口方向，不写设计细节。

### 3.5.1 PC Vision 的边界（P0002）

PC Vision 只做一件事：把视频流变成**每个车位的 EMPTY / OCCUPIED**，外加一个内部
`changed_ratio` 供调参。它：

- **消费** `GET http://<device-ip>/stream`，**不**联系摄像头节点的任何其它接口；
- 车位坐标最终由人工确认后写入 `vision/config/parking_spots.json`。P0002.1 的
  `Auto Detect` 只是提出候选的助手（纯 OpenCV 几何，无 AI），**它不是权威来源**，
  也永远不会覆盖人工调整过的结果；
- 不产生路线、不产生预约、不驱动 LED —— 那些属于 Backend 及之后；
- 在 ESP32 上不做任何推理，也不向 ESP32 反向下发任何东西（单向视频）。

## 3. 边界规则（必须遵守）

### 3.1 摄像头节点不理解业务

ESP32-S3 固件里**不允许**出现这些概念：

```
parking space      reservation     route
vehicle state      slot / stall    occupancy
```

固件唯一的业务输出是**一条视频流**。它不知道画面里是停车场还是别的什么，
也不知道有没有车、哪个车位空着。

> **P0008 修订**：相机节点现在会**读**一个业务文档（`parking_state.json`）去点灯，
> 所以 `occupancy` 确实进了固件，但**只是读字符串比较**（`EMPTY` / `OCCUPIED`）。
> 它仍然不产生、不存储、不转发任何业务状态，也没有入站业务接口。这一条修订的完整
> 边界写在 §3.6，不要把它当成「3.1 失效了」。

### 3.2 视频流是唯一的对外业务接口

PC Vision 只通过 HTTP 拿画面，不反向控制摄像头节点。

```
ESP32-S3-CAM  ──HTTP GET /stream──▶  PC Vision
              （单向，无业务控制通道）
```

状态页 `/` 和 `POST /api/ota/check` 是**运维接口**，不是业务接口：
前者只读展示自身状态，后者只触发自升级检查。两者都不知道也不关心停车场。

P0008 加了一条**出站只读**业务通道（设备 → PC Vision），这是 §3.2 在“没有任何入站
业务接口”之外唯一放开的地方；放开的理由和边界见 §3.6。

### 3.3 视觉推理不上 ESP32-S3

ESP32-S3 只负责拍摄和传输。识别、定位、路径规划都在 PC 上做。

### 3.4 业务状态不落在摄像头节点

车位状态、预约信息由 Backend 持有。摄像头节点不持久化任何业务状态 ——
本固件用 NVS 只存两样东西：Wi-Fi 凭据（命名空间 `wifi`）和
ESP-IDF 自己的 PHY 校准数据。**没有业务数据。**

P0008 的灯带状态同样不落盘：它只活在 `led.c` 的一个 RAM 帧缓冲区里（§3.6）。

### 3.5 OTA 服务的边界

`tools/ota-server/` 不是「平台」，它只做两件事：

```
GET /manifest.json
GET /firmware/<version>/parking-lot-cam.bin
```

明确**不做**：用户系统、登录、数据库、设备管理、MQTT、fleet management、
firmware dashboard、云端部署要求、遥测后端、远程视频、设备账号。

它不知道有几个设备、设备是谁的、设备在哪 —— 谁都能 GET，它也从不主动联系设备。
设备是 pull 模型，OTA 服务永远不需要「推送」或维护设备列表。

固件侧的 OTA 客户端同样只认「版本号 + 一个二进制 + 一个 SHA256」，
不理解、也不需要理解这个二进制是从哪来的。

### 3.6 车位状态灯的边界（P0008）

灯带挂在**相机节点自己的 GPIO14** 上（不是独立 MCU，也不是 Backend 的外设）。
它给相机节点带来的唯一新能力是**一条出站只读请求**：

```
camera ──GET http://<pc>:8010/out/parking_state.json──▶ PC Vision
              （500 ms，只读，只拿 spots[id].state）
```

四条必须同时成立的限制：

1. **只读，只出站。** 设备不向任何地方写业务数据，也不开新的监听端口；
   `POST` 在整个固件里只有一个，就是 `/api/ota/check`（运维）。
2. **不持久化。** 拿到的状态只活在 RAM 里一个帧缓冲区里，不写 NVS。
   （NVS 仍然只有 Wi-Fi 凭据 + PHY 校准。）
3. **不推断，只转写。** `EMPTY` → 绿、`OCCUPIED` → 红，其余（包括 `UNKNOWN`）
   → 灭；`route.json` 的 `ok == true` 且目标车位为空 → 黄。固件不能看 `changed_ratio`、
   不能自己定阈值、不能猜；先读 `ok` 再读 `target_spot`。
4. **断链就灭。** 拉不到新状态就整条熄灭，**不得**保留上一帧颜色。

颜色语义：绿 = 空位，红 = 占用，黄 = 导航目标（`out/route.json` 里 `ok` 为真时的
`target_spot`）。

**黄只覆盖绿，不覆盖红**：目标车位如果已被占，显示红。黄的意思是“来这里”，指着一个
已经被占的车位叫人过去是唯一不能做的事；而且这样一来两个状态会自己互相纠正。

**导航结束必须有人明说。** `route.json` 不会自己消失，所以页面取消导航或到达车位时调
`GET /api/route?clear=1`（写 `ok=false, code=navigation-ended`）。没有这个，停止导航后
会留下一颗永远不灭的黄灯——只有灯带上看得见的、页面上早已不存在的状态。

为什么灯在相机节点上而不是独立 MCU：沙盘尺度下一条灯带就在一个盒子里，
没必要为一个显示器开一块板子、一条链路和一个新协议。代价写在这里：
**「PC Vision 不反向联系相机节点」这条规则现在多了一句‘相机节点会主动去读它的状态’**，
以及 `src/serve.py` 必须显式 `--host 0.0.0.0`（它默认只绑回环，设备拉不到）——
而那个 handler 会把整个 `vision/` 目录不加鉴权地暴露给局域网。

## 4. 已确定的对外契约

| 项目 | 值 |
|---|---|
| 视频协议 | HTTP/1.1 + `multipart/x-mixed-replace` |
| 视频端点 | `GET /stream` |
| 状态页 | `GET /`（只读） |
| OTA 手动触发 | `POST /api/ota/check` |
| 编码 | JPEG（由 OV3660 传感器直接输出） |
| 分辨率 | 800x600 (SVGA) |
| 端口 | 80 |
| 设备地址 | `http://<device-ip>/stream`，IP 由 DHCP 分配，串口打印 |
| 配网 | SoftAP `ParkingCam-XXXX` + `http://192.168.4.1` |
| 升级 | `GET <ota-server>/manifest.json` → `GET firmware_url` → SHA256 → A/B 槽位 |
| 车位状态（P0008，出站） | 设备→PC：`GET http://<pc>:8010/out/parking_state.json`（`parking_state/1`，只看 `spots[id].state`） |
| 导航目标（P0008，出站） | 设备→PC：`GET http://<pc>:8010/out/route.json`（`route/1`，先 `ok` 再 `target_spot`）；PC 侧取消/到达时 `GET /api/route?clear=1` |
| 车位状态灯的接线 | DIN = GPIO14，RMT（不使用 LEDC，已与相机 XCLK / 屏幕背光错开） |

选择理由：MJPEG over HTTP 是最简单、最成熟、后续 Python/OpenCV 最容易消费的方案
（`cv2.VideoCapture("http://<ip>/stream")` 直接可用），不需要在嵌入式侧
研究任何新的视觉算法或通信协议。
