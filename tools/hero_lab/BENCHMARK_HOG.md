```

```

## Input

```
来源: PC 侧 MJPEG relay  http://127.0.0.1:8021/stream（不占板子第二路流）
帧:   800×600 JPEG
窗口: 64×64（HOG 8×8 cell / 2×2 block / stride 8 / 9 bins → 1764 维）
```

## Dataset

```
正样本   124（人工拖框，含车顶标记的整车）
负样本   496（每帧自动采 4 个：其它车/空位/道路/LED/闸机/边缘）
整帧     124

采集批次 sess1 42 · sess2 46 · sess3 36
位置覆盖 x 23~753, y 85~513（含左右边缘）
bbox    宽 43~115, 高 37~103, 长宽比 0.48~2.84（含各朝向）

切分: 按「采集批次」整批切，同批的连续帧绝不跨 train/val
```

## Training

```
分类器  cv2.ml.SVM_LINEAR, C=0.01
增强    仅正样本 ×4：旋转 ±15°、亮度 ±15%、对比 ±15%、轻高斯模糊、JPEG 45~90
        （不做改变几何结构的增强）
特征    1764 维，每窗口一次点积
```

|---|---|---|---|---|---|---|
| sess1 | 0.976 | **1.000** | 42 | 1 | **0** | 168 |

| sess3 | **1.000** | **1.000** | 36 | 0 | **0** | 144 |

```
frames     202
```

| 验收线 | 实测 | 判定 |
|---|---|---|
| **≥ 20 FPS** | **209 FPS**（p95 5.4 ms） | ✅ 远超 |
| **recall ≥ 95%** | **98.4%**（124 中漏 2） | ✅ 通过 |
| **误检很少** | **0 / 496** | ✅ 通过 |

## 结论：**值得继续** ✅

HOG + Linear SVM 在这个任务上表现非常好，而且**快得离谱**（4.8 ms vs 现在 production 红掩码的 7~22 ms，
vs 模板匹配的 155 ms）。它还能**覆盖边缘**——红掩码在边缘也会掉，而 HOG 是整窗分类，不受"红色像素少"影响。

## 诚实边界（还不能下结论的部分）

1. **不是跨天验证**。三个批次是同一张桌子、同一套灯光、同一次布置。`recall 0.984` 证明的是
   「同一场景下的新位置、新朝向」，不是「换灯光/换桌子之后」。
2. **负样本是自动采的**，分布由采样网格决定，不是"难负样本"。真实场景里的困难样本
   （半个车、被挡住的车、车的影子）没有针对性覆盖。
3. **检测到的是 bbox，不是方向**。方向仍需在 bbox 内用几何方法（`red_arrow.py` 的 PCA 主轴 + 头尾）算。
4. **N=124 偏小**。按经验，这个数字上的 98% 置信区间大约 ±3%。

## 建议的下一步

1. **再采 2 个批次**：不同时段（灯全开/半开）+ 车贴边/被部分遮挡 → 看 recall 掉多少
2. 如果稳，就把 `live_detect.py` 的滑窗接到 bbox 输出，方向仍在 bbox 内用几何法算
3. 到这步再谈是否替换 production 的 `red_arrow.py`（**现在不动**）
