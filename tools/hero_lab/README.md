# hero_lab — 车辆掩码实验台（**不属于生产链路**）

## 这个目录是什么

现有产品用 `vision/src/vehicle.py` 的 `red_mask()` 产出车辆掩码，再由同一模块的特征段
（PCA / `minAreaRect` / `taper` / 涂装端定车头）算出契约字段。本目录放的是**掩码的候选实现**，
用**运行期替换**的方式接进同一套特征段来对比：

```python
with lab.mask_provider(lab.candidate_red_mask):
    poses = vehicle.locate_all(frame)      # 生产文件一行未改，连 import 期都没改
```

**铁律**

1. `vision/` 下的任何东西**不得 import 本目录** ✗（生产链路不认识实验代码）。
2. 本目录**只读** `vision/` 的模块 ✓，**不写入** ✓，不改 `config/` ✓。
3. 候选不能达标之前，不进产品；结论以实测为准 ✓，不挑选样本 ✓。
4. 拷贝来的函数必须**逐像素可复现原函数** ✓ —— `compare.py` 每次运行都自检（`copy check`），
   一旦漂移立刻失败 ✓（否则所有对比都没有意义）。

## 怎么跑

```bash
python tools/hero_lab/compare.py            # 3 张种子帧 + 合成旋转整圈 + 拷贝自检
python tools/hero_lab/compare.py --live 60  # 追加实况 60 帧（检出率 + 掩码倍数 + 每帧耗时）
```

## 候选内容（两个改动，各有实测依据）

| 编号 | 改动 | 依据 |
|---|---|---|
| **B1** | 按**面积**剔除车位灯/地面标识（阈值 300） | 实况 90 帧：车涂装 **421–933 px** ✓，其余黄块 **17–285 px** ✓ → 中间有空隙 ✓。形状试过**失败** ✗（"小且细长"只删掉 10 个中的 1 个 ✗，因为灯是 5x16–6x30 但地面标识是 5x8–16x9，小而方 ✗）；颜色**不可能** ✗（灯 H23-28/S90-114/V131-142 vs 涂装 H23-33/S90-197/V70-195，区间重叠 ✓）。 |
| **B2** | 涂装暗侧改用**近场最暗段中位数**；切分门限改为"沿车方向 vs 路面"的中点 | 右侧帧车顶真值 **V≈50**（扫描线 `59 53 52 52 50 49`），路面 155–168 ✓；但产品取**整条射线中位数**，车顶只占前 22% → 读成 **131** ✗ → 对比度算成 16 级（门限 40）✗。分段后同方向读 **49** ✓（对比度 79 级 ✓）。 |

## 结论（本次，已记录以免重复劳动）

**B 组候选的第一版实现失败** ✗ —— 不是"方向错误"的结论，而是"这一版实现不达标" ✓：

- B2 的近场统计在**光足的两帧上把车顶切掉了一部分** ✗（切分门限偏紧 ✗），
  与之前离线测得的"对比度 79 级 ✓"并不矛盾：**统计量对了，切分点错了** ✓；
- `right_up` 帧上 B1 之后仍被拉成 136px 高 ✗ → 说明该帧的桥接**还有第二个来源** ✗
  （B1 只剔了 ≤300px 的块；需要逐阶段量 `drop_small_blobs → paint_side → attach → merge → 填洞`
  到底是哪一步长出 136px ✗），**本轮未定位** ✓；
- 因此**不能**说"规则可解"或"规则不可解" ✓ —— 目前只能说：**这一版规则候选不如生产** ✓。

**下一步（需要先补数据再谈模型）**：

1. 逐阶段插桩，定位 `right_up` 帧 136px 的第二处桥接（不猜 ✗）；
2. 给 3 张种子帧补**人工四点标注** ✓ → 才有 IoU 这个客观指标，而不是靠"倍数/伸长比"间接判断 ✓；
3. 在此之前**不训练模型** ✗：无标签（n=3 ✗）、无多场景数据 ✗、无客观指标 ✗，
   任何"网络更准"的说法都不可复现 ✓。

## 2026-10-17：91 张人工标注的实测（**这是目前唯一的客观基线**）

数据：`vision/data/labels/annotations.jsonl` 共 93 条，91 张图片可用（2 张是我误删的 ✗，评估时跳过并记录）。
真值 = 人工四点四边形 + 存储的箭头；**从未使用管线自己的输出作为真值** ✓。
跑法：`python tools/hero_lab/eval_labels.py --worst 8`

| 指标 | A 生产管线 | B 候选掩码（B1+B2） |
|---|---|---|
| 检出率 | 90/91 (99%) | **91/91 (100%)** |
| **IoU（对人工四边形）** | **0.504** ✗ p10 **0.000** ✗ | **0.675** ✓ p10 0.410 |
| 中心误差 | 17.2 px ✗ p90 230 px ✗ | **4.7 px** ✓ p90 18 px |
| 长轴误差 | 5.8° ✓ p90 **68°** ✗ | 5.2° ✓ p90 **17°** |
| 车头误差 | 17.0° ✗ p90 **174°** ✗（前后颠倒） | 10.7° ✓ p90 32° |
| 车头给出率 | 85% | 90% |
| 面积比 | 0.86× | 0.81× |
| **耗时/帧** | **72.7 ms** ✓（≈ 帧间隔） | **195 ms** ✗✗（2.7×，会掉帧） |

按条件拆分（这就是"右侧不准"的量化 ✓）：

| 区域 | A IoU / 长轴误差 | B IoU / 长轴误差 |
|---|---|---|
| 画面左半 (n=47) | 0.548 / 5.0° ✓ | 0.683 / 5.2° ✓ |
| **画面右半 (n=44)** | **0.414 / 15.4°** ✗ | **0.656 / 5.5°** ✓✓ |

配对比较：**B 在 62 帧更好、18 帧更差、11 帧并列** ✓。

### 结论（有数字，不是感觉）

1. **生产管线的真实精度远低于"屏幕上看着对"** ✗：IoU 中位 0.50，p10 = **0.00** ——
   有 8 帧以上掩码与车**完全不重叠** ✗（检出 True 但框在别处 ✗），这是**误检**，不是"框小" ✗。
2. **左右不对称被量化了** ✓：右半 IoU 0.41 / 长轴 15.4°，左半 0.55 / 5.0° ✗。
3. **确定性修复（B）确实有效** ✓：IoU 0.50→0.68、中心误差 17→4.7px、右侧差距基本消除 ✓。
4. **但 B 现在还慢 2.7 倍** ✗（195ms > 70ms 帧间隔）→ **瓶颈是速度，不是精度** ✗。
5. **所以现在还不该训练模型** ✗：一个确定性的改动已经拿到主要收益 ✓，
   剩下的问题是"把它变快"，而不是"让网络来学" ✗。

### 下一步（按证据排序）

1. **给 B 提速**：`_ray_near_level` 的 16 射线 × 4 段是全部开销 ✗（195ms）→ 只算必要的方向、
   把 4 段改成 2 段、或向量化 ✓，目标是 < 70ms ✓；
2. **看那 8 帧 IoU=0 的图** ✗（`ann-20261017-092609/092631/092853/093329/093735/093900/094244/094257` ✓）
   —— 误检的来源要定位（很可能是灯/标识再次参与 ✓，但 B 也不该出现在这 8 帧 ✗）；
3. 这两步之后**再重测**，若 B 优化后仍有个别帧明显差 ✓，**那几帧**才是模型该学的东西 ✓
   —— 不是整条管线 ✗。

## 2026-10-17（下午）：参考帧差分被证否 ✗

想法：相机和沙盘都是静止的，车是画面里唯一的变化 → 用"空场景参考帧差分"拿**整个车身**（不只是涂装），
而且**对黄灯免疫**（灯在参考帧里也在 ✓）。开销实测 4.6ms ✓。

实测（139 张人工标注，同一批真值）：

| 方案 | IoU 中位 | 完全错 (<0.30) | 好 (>0.70) | 检出 | 耗时 |
|---|---|---|---|---|---|
| A 生产 | 0.457 | **39 帧** ✗ | 12 | 135/139 | 70 ms |
| B 候选掩码 | **0.584–0.675** ✓ | 11 帧 ✓ | **35** ✓ | 128/139 | 79 ms |
| **C 参考帧差分** | **0.012** ✗ | **139 帧** ✗✗ | 0 | **0/139** ✗✗ | 19 ms |
| C + 亮度归一化 | 0.015 ✗ | 139 帧 ✗ | 0 | 0/139 ✗ | 66 ms |

**原因（量化）**：新采的参考帧（11:53）与标注帧（09:11–11:2x）在 **40.4%** 的像素上不同 ✗ ——
车的面积只占 0.3% ✓，所以这不是车，是**现场光照/曝光在两次采集之间变了** ✓。
静态参考帧在这种条件下没有意义 ✗；全局亮度归一化也救不了（0.015 ✗），因为变化不只是亮度偏移。

所以 `capture_reference.py` / `diff_reference.py` 留在仓库里，是为了**这个否定结论可复现** ✓，
不是为了继续用这个方案 ✗。

## 结论：剩下真正可选的只有两条

1. **B 用于"车在哪、朝哪"已经够用** ✓ —— 中心 4.7px ✓、长轴 5.6°(p90 15°) ✓、车头 11° ✓；
   不够的是**范围**（IoU 0.58–0.67 ✗，66% 的失败是正对镜头时只圈到 1/4 车身 ✗）。
   → 若产品的需求是导航位姿 ✓，**B 达标，不必再投入** ✓。
2. 若**必须**要准确的车辆范围 → 两条路：
   - **ArUco/AprilTag 标记** ✓（项目已有 `tests/aruco_check.py` ✓）：位姿精确 ✓、不怕光照和灯 ✓、
     开销极小 ✓；代价是**车顶贴一张标记**（物理改造）+ 标记必须可见 ✗；
   - **学习型分割** ✓：139 张标注够训一个小模型 ✓，它能学到"正对镜头时的车身形状"✓ ——
     这正是规则做不到的部分 ✓；代价是 torch 依赖 + 训练/评估/维护（约一周）✗。**排最后** ✗。
